# Задание оператору: удалённый расчёт W2-P004 P2-1 на Vast.ai (вариант В)

Ты — LLM-агент (Codex CLI или Pi) с полным доступом к компьютеру пользователя (Windows 10,
папка проекта `T:\test_python\submoon-research`, WSL Ubuntu-24.04), к глобальному Python с
`vastai` и `paramiko`, к SSH-ключу `~/.ssh/vast_agent`. Задание выполняется **в две сессии**:
вечером (проверка, аренда, развёртывание, проверка запуска, после чего пользователь выключает
компьютер) и утром (выгрузка, удаление, отчёт). Перед любыми действиями прочитай этот документ
полностью.

Версия 2 (2026-10-09, вечер): исправлен ложный отказ стража полинома IAS15 у движка B
(W2-I015), стенд v4 разделяет обязательный набор и расширение и сам останавливается к сроку
(`run_deadline_utc`), добавлены действия `wrapup` и `finish --partial`.

## 0. Обязательное чтение и правила

1. `AGENTS.md` (правила проекта) и `docs/compute_policy.md` (аренда). Справка по CLI —
   `vastai_cli_cheatsheet.md` (разделы 7–14).
2. План аренды: `docs/compute/W2_P2-1_rental_plan_v1.md`. Approval: `scratch/p2_rental/approval.json`.
3. Научные критерии (не менять!): `docs/tasks/W2_compiled_mode_admission_v1.md` §3.1, §3.2, §7.
4. Документ передачи: `docs/handoffs/W2_T008_session_20261009.md` (контекст, пакеты 1–6).

Жёсткие ограничения:

- **Деньги:** только в пределах approval: 1 инстанс, ставка ≤ $0.50/ч, ≤ 16 ч от создания, всего
  ≤ $8, не более 3 попыток аренды. Любой выход за пределы — остановиться и спросить пользователя.
- **Секреты:** не печатать, не сохранять и не копировать на сервер ключи API и SSH. Не включать
  их в файлы проекта, журналы, отчёты.
- **Научный код и критерии не менять.** Разрешено чинить только транспорт `scripts/vast_p2.py`
  (сеть, пути, CLI), с записью исправления в журнал. Если падает научный гейт (pytest/ruff/quick
  на сервере или в WSL) — не обходить, а остановиться (на сервере — `destroy`) и сообщить
  пользователю.
- **Файлы:** не удалять локальные файлы; результаты не перезаписывать (скрипт пишет только
  новые файлы в `runs/W2-P2-1*`). Без git push.
- **Журнал:** `scripts/project.py track add` с фактическим `--expected-revision`; owner/actor
  твоего агента, например `codex-p2rental-20261009` (или `pi-p2rental-20261009`). Если после
  `track add` остаётся `tracking/.write.lock` от твоего процесса — убедись, что писатель завершён,
  и удали его (это твоя среда, у тебя есть право удаления).
- Запускать скрипты глобальным Python Windows из корня проекта:
  `python -X utf8 scripts/vast_p2.py <action>` (как прежние `vast_w2.py` / `vast_cpu_matrix.py`).

## 2. Вечер: аренда и развёртывание (платно, в пределах approval)

1. `python -X utf8 scripts/vast_p2.py rent` — берёт первое (самое дешёвое за ядро-час) предложение
   из `offers.json`; повторно — следующее (или `--offer-id N` из списка). Пишет
   `scratch/p2_rental/rental.json`.
2. `python -X utf8 scripts/vast_p2.py wait` — до 40 мин ожидания `running`; при неуспехе скрипт
   сам удаляет инстанс. Тогда можно повторить `rent`, всего ≤ 3 попыток.
3. `python -X utf8 scripts/vast_p2.py deploy` — загрузка пакета, сверка SHA манифеста, запуск
   удалённого сценария (`/workspace/p2_start.sh`, лог `/workspace/p2_<iid>.log`). Печатает
   `run_deadline_utc` = создание + 13.5 ч: к этому сроку стенд сам останавливает незавершённые
   задания (они записываются как `partial`, «остановлено сроком»), подводит итог и пишет
   `done`. Запас до предела 16 ч — на утреннюю выгрузку.
4. Сразу записать в `tracking/runtime.json` процесс: run_id `W2-P2-1-<iid>`, instance_id,
   host `vast.ai`, статус `running`, created_utc, deadline (created + 16 ч), run_deadline_utc,
   команда остановки `python -X utf8 scripts/vast_p2.py finish`, лог, лимиты ($0.50/ч, $8).
   Обновить `updated_utc`.
5. Каждые 5–10 мин: `python -X utf8 scripts/vast_p2.py status`. Этапы `/workspace/p2_status`:
   `setup` (apt + pip + сборка reboundx, до ~60 мин) → `gates` (pytest четырёх файлов, ruff,
   диагностика W2-I015 ~1–2 мин, quick ~несколько мин) → `running … workers=… deadline=…`.
   Если `FAILED <этап>` — прочитать хвост лога. Транспорт/окружение (apt, сеть pip) — можно один
   раз повторить на новом инстансе (`destroy`, затем `rent`, …) в пределах попыток. Научный гейт
   (pytest/ruff/quick) — **не обходить**: `destroy`, запись issue, сообщение пользователю.
   Строка `diag_ias15_guard: код 1` в логе — не гейт; отметить в W2-T010.
6. Когда этап `running` и в `progress.json` растёт `done` (сначала идёт обязательный набор:
   сотни коротких заданий за минуты), проверить: `workers` ≈ числу физических ядер (и квоте
   cgroup, если она меньше); нет ошибок в логе.
7. Записать в журнал W2 (`W2-T010` обновить): instance_id, CPU, ставка, workers, run_deadline_utc,
   первые цифры прогресса, итог bguard; next_action — утренний `finish`.
8. Сообщить пользователю: инстанс, ставка, что стенд закончит не позже `run_deadline_utc`
   (самые длинные задания 10 000 лет и B 1 000 лет могут не успеть — тогда они сохраняются как
   частичные с достигнутым временем), что компьютер можно выключить, и что утром нужно
   запустить тебя снова с этим заданием (раздел 3).

## 3. Утро: проверка, выгрузка, удаление

1. `python -X utf8 scripts/vast_p2.py status`.
   - `done exit=0` или `done exit=1` — расчёт закончен (exit=1 означает «обязательные ступени не
     пройдены/не завершены» — это научный результат, его тоже выгружаем). → шаг 2.
   - `running` — стенд ещё считает (до `run_deadline_utc`). Сообщить пользователю прогресс
     (`progress.json`: done/planned, stopped по ступеням). Если пользователь хочет результат
     сейчас **или** с создания прошло ≥ 15 ч — `python -X utf8 scripts/vast_p2.py wrapup`
     (стоп-файл: задания останавливаются, стенд пишет итог), затем `status` раз в минуту до
     `done` (обычно 1–3 мин). Если за 15 мин `done` не появился — `finish --partial`.
     Иначе — ждать (`status` раз в 10–15 мин) до `done`.
   - `FAILED …` — прочитать лог; `finish --partial` (выгрузит логи и всё, что есть).
   - инстанс исчез (`provider: not_found`) — записать issue (вероятно отзыв провайдером),
     сообщить пользователю; данные на сервере потеряны, локальных частичных нет.
2. `python -X utf8 scripts/vast_p2.py finish` — проверяет этап `done`, выгружает, сверяет SHA,
   распаковывает в `runs/W2-P2-1-<iid>/` и `runs/W2-P2-1-quick-<iid>/`, затем удаляет инстанс и
   проверяет удаление. Если выгрузка не удалась — инстанс НЕ удаляется; повторить `finish`.
   Удаление без выгрузки (`destroy`) — только по прямому указанию пользователя.
3. Проверить в Vast, что инстансов не осталось (`vastai show instances`), и зафиксировать
   фактический расход: `elapsed_hours`, `upper_cost_usd` из `rental.json`; по возможности
   сверить с биллингом аккаунта (без секретов).
4. Скопировать доказательства (малые файлы) в `results/evidence/W2_P2-1_remote_<iid>/`:
   `summary.json`, все `level_*.json`, `progress.json`, `diag_ias15_guard.json`, `summary.json`
   из quick-каталога, удалённый лог, `p2_pip_freeze.txt`, `rental.json` (без секретов),
   `bundle_info.json`, SHA-256 архива результатов. `jobs.jsonl` остаётся в
   `runs/W2-P2-1-<iid>/` (крупный, git-игнорируется); его SHA-256 указать.
5. Отчёт `reports/operations/W2_P2-1_remote_<YYYYMMDD>.md`: машина, ставка, время, расход,
   ход развёртывания, гейты и диагностика W2-I015, итог обязательного набора по ступеням
   (`summary.json` → `levels`: passed/counted, нарушения P2-Q1/Q2, проблемы), расширение
   (`extension_levels`: passed/complete/counted, число остановленных сроком), длительность, сбои
   и исправления транспорта. Научную интерпретацию не добавлять — её делает основной
   исполнитель W2-T008.
6. Журнал W2: `W2-T010` → done (refs: отчёт, evidence); check об удалении инстанса и
   выгрузке с SHA (passed/failed по факту); `tracking/runtime.json` — процесс удалить из списка,
   записать note с итогом. Проверить `python scripts/project.py validate`.
7. Сообщить пользователю: обязательный набор — одна строка на ступень; расширение — сколько
   заданий завершено/остановлено; расход; где лежат отчёт и данные; следующий шаг — разбор
   основным исполнителем (Claude, W2-T008).

## 4. Сбои: что делать

| Ситуация | Действие |
|---|---|
| bguard в WSL: pytest/ruff не прошли | Не арендовать; сообщить пользователю |
| bguard: диагностика «НЕ ПОДТВЕРЖДЕНО» | Аренду продолжать; отметить в W2-T010 и сообщить |
| preflight не пройден | Ничего не арендовать; сообщить, чего не хватает |
| Нет подходящих предложений | Не расширять фильтр; сообщить пользователю ближайшие варианты |
| Инстанс не стартует за 40 мин | `wait` удалит сам; следующая попытка `rent` (≤3) |
| SSH не подключается после running | 2–3 повтора с паузой; иначе `destroy` и следующая попытка |
| FAILED setup/apt/pip | Повторная аренда допустима (≤3 попытки), лог сохранить |
| FAILED pytest/ruff/quick | Не обходить: `destroy`, issue в журнал, сообщить пользователю |
| `deploy`: «до срока стенда меньше 3 ч» | Аренда слишком затянулась: `destroy`, сообщить пользователю |
| Утром ещё `running`, пользователь ждёт | `wrapup` → `done` → `finish` |
| Расход приближается к $8 или 16 ч | `wrapup`; если нет `done` за 15 мин — `finish --partial`; сообщить |
| Ошибка в `vast_p2.py` (транспорт) | Исправить минимально, записать в журнал, продолжить |

## 5. Что считать выполненным

Вечер: bguard пройден (или отмечен), инстанс в состоянии `running`, удалённый этап `running`,
`progress.done` растёт, записи W2-T010 и runtime.json созданы, пользователь уведомлён. Утро:
результаты выгружены со сверкой SHA, инстанс удалён и это проверено, расход в пределах $8,
evidence и отчёт созданы, журнал и runtime.json обновлены, `validate` проходит, пользователь
уведомлён.
