## Цель и границы

Получить минимально достаточный, воспроизводимый и ресурсно обоснованный маршрут от текущих результатов к численному допуску W1/W3. Оптимизировать не только скорость одного шага, но стоимость **достоверного результата**, включая диагностику, повторный расчёт, простои и вероятность потери данных.

Не перестраивать весь проект, не менять физическую модель и статистический критерий ради положительного исхода. Не считать этот план доказательством завершения W2. Не планировать заранее точные сроки разработки или стоимость новых длинных прогонов без измерений.

Основания: W2-C066/C068, W2-I033/I034/I036, W2-D022/D026/D036, W2-R022; `docs/tasks/W2_compiled_mode_admission_v1.md` (включая P3/P4), `docs/tasks/W2_P2-2_plan_v1.md`, `docs/tasks/W1_implementation_protocol_v1.md`, `docs/validation_protocol.md`, `RESEARCH_ROADMAP.md`, `configs/resources.yaml`.

### Что сохранить и не делать заново

- P2-2a принят как набор данных; результат D–T остаётся inconclusive, не production-допуск.
- Причина BLAS-различий найдена; `exact-fsum-v1` и исторический `legacy-blas` сохраняются.
- Отчёт и W2-R022 уже уточнены 17.10 по хаосу, high-e и B. Не повторять эти изменения и не стирать первоначальную историю.
- Отказ B воспроизведён: шаг 0.482 ULP не продвигает временную метку. Не повторять часовой расчёт без новых диагностик; первопричина уменьшения шага ещё неизвестна.
- Сохранение units.json уже есть; требуется довести проверку и использование до правильного контракта, а не создать второй несовместимый формат.
- Наличие многочисленных modified/untracked файлов — факт рабочего дерева, не доказательство их дефектности. Не удалять/откатывать чужую работу и не выполнять массовый commit без разбора состава.

## Пакет B. Проверки, окружение и воспроизводимость

### OPT-05 — Сделать запуск проверок честным и наблюдаемым

**Приоритет:** вместе с пакетом A. **Зависимости:** нет для исправления отчётности.

Общий exit code ненулевой при любом обязательном failed; сохранять полный traceback и машинную сводку по шагам, а не только хвост. Различать успешное выполнение диагностики и успешную интеграцию. Переименовать «full suite» с исключённым test_l1_acceptance; ожидаемые skip и незапущенные тесты перечислять отдельно. Разобрать L1 timeout отдельно: измерить запуск/сборку/FS и проверить, есть ли только инфраструктурная причина; не увеличивать timeout вслепую. Короткие проверки отделить от часовых диагностик, запуск последних явно выбирается. Новая проверка получает новый ID/UTC и не перезаписывает прошлый лог.

**Готово:** искусственный failed не даёт зелёного общего итога; все запущенные/пропущенные/исключённые тесты восстановимы; Windows и WSL проверяют свой заявленный набор. Обязательные REBOUNDx-тесты выполняются в WSL, Windows skip их не закрывает.

### OPT-06 — Использовать замороженные входы как вход расчёта, а не побочный файл

**Приоритет:** до новых сравнений D/T/B и D–D′. **Зависимости:** OPT-03/04.

Новые run получают проверенный самостоятельный артефакт стартов и физического контракта. Разделить два вида проверки: (а) генератор воспроизводит замороженный набор; (б) расчёт/анализ соответствуют уже замороженным входам, без требования пересчитывать их другой CPU-библиотекой. Приёмщик пока всегда регенерирует старты; переход к чтению артефакта требует проверки SHA против независимого доверенного manifest, происхождения и состава, не слепого доверия локальному JSON. Старые run остаются legacy; если нужен переносимый файл входов, создать новый связанный артефакт из подтверждённого исторического маршрута и проверить исходные fingerprints. Не дописывать его в старый run.

**Готово:** новый run проверяется на целевых Windows/WSL по одним буквальным входам; намеренная подмена отклоняется; отдельный тест генератора выявляет его изменение; старые run не меняют идентичность.

### OPT-07 — Зафиксировать проверенную среду, не обновлять зависимости ради исправления вслепую

**Приоритет:** до подтверждающей серии. **Зависимости:** OPT-02/06.

Проверки генератора и короткого интегрирования — на целевых средах, без обещания одинаковости на любой платформе.

**Готово:** воспроизводимая установка и короткий сквозной тест; зависимости не сдвигаются незаметно; доступные балансы/исходы проходят заранее заданные допуски. При ограничении сети/пакетов отсутствие чистого восстановления явно остаётся ограничением.

## Пакет C. Установить и исправить первопричину W2-I034

### OPT-08 — Разделить причины отказов и усилить диагностику адаптации B

**Приоритет:** научный критический путь. **Зависимости:** пакеты A/B для сохранения результатов.

Разделить ошибки «нет продвижения времени», «вышли за bound», «несогласован dt_done», «не воспроизведён конец полинома». Сохранять t, ULP, requested/actual/next dt, ограничения шага, параметры адаптации и сходимости; по триггеру — полное состояние до ошибочного шага и необходимые численные данные. Диагностический скрипт обязан отказаться до интеграции при несовпадении идентичности стартов/B-контракта; сейчас identity только печатается. По умолчанию ограничить расходы/объём логов; трассировать проблемное окно или кольцевой буфер, а не писать весь многомиллионный ряд.

**Готово:** по отчёту различим механизм ошибки; сохранён короткий контекст, достаточный для проверяемого replay; никакие guards не ослаблены. Первопричина малого шага ещё не считается найденной.

### OPT-09 — Получить воспроизводимый короткий replay и провести различающие эксперименты

**Приоритет:** до выбора исправления IAS15. **Зависимости:** OPT-08.

Если одного сохранённого физического состояния недостаточно, проверить нативное сохранение REBOUND/REBOUNDx вместе с адаптивной историей и параметрами сил. Нельзя обещать, что state restart воспроизведёт тот же шаг отказа. Сначала доказать воспроизведение проблемного окна без изменений. Только затем сравнивать кандидаты причин:

1. накопление большого значения времени (перенос начала отсчёта);
2. потеря относительной точности из-за дрейфа абсолютных координат — диагностические перенос/галилеев boost с правильным преобразованием всех состояний;
3. поведение оценщика шага и predictor-corrector;
4. реальные тесные проходы всех значимых тел и возможная ошибка сил/событий.

Эти варианты — гипотезы, не установленная причина. Проверять автономность/временные зависимости сил перед переносом эпохи. Не менять несколько факторов одновременно без контрольного варианта. При невозможности точного native replay использовать контролируемые state restarts как иной эксперимент и обозначать это ограничение.

**Готово:** короткий исходный replay воспроизводит отказ либо явно зафиксировано, почему это не достигнуто; результаты различают хотя бы основные причины. Новый полный часовой проход выполняется только ради получения недостающих данных/checkpoint, а не повторения известного лога.

### OPT-10 — Минимальное исправление B и регрессионный допуск

**Приоритет:** до использования B как резервного production-маршрута. **Зависимости:** OPT-09.

Выбирать изменение только по доказательству причины. Не подменять dt, не продвигать время nextafter, не снимать защиту и не объявлять перенос эпохи готовым решением заранее. Новая версия B сохраняет согласованность времени, координат, dense-сегмента, событий и checkpoints. Проверить короткие аналитические и high-e пределы, плохие шаги, длинные временные метки и сходимость. Затем исходная орбита до 1000 лет и достаточное покрытие диапазона времён/режимов для будущих 10000 лет.

**Готово:** исходный случай завершён без обхода guards; поведение и научные исходы прошли независимые/уточняющие проверки. Один успешно завершившийся повтор — необходимое, но не достаточное условие. Если надёжный B в нужной области не получен, оставить unresolved и вернуться к выбору режима отдельным решением.

## Пакет D. Уменьшить неопределённость high-e без смещения выборки

**Готово:** версия политики переключения, матрица проверок и новые fingerprints; передача не теряет события и не принимает уже загрязнённое состояние без контроля.

## Пакет E. Сходимость и новый подтверждающий дизайн

### OPT-14 — Адресно разобрать 17 расхождений и контрольные орбиты

**Приоритет:** до выбора достаточного режима. **Зависимости:** точные входы OPT-06; high-e ветви требуют OPT-12.

Особые случаи: `himalia:canonical_volume:0012`, два contact↔escape Ганимеда, 12 случаев с high-e. Сравнить D/T/B и дополнительное уточнение; проверить разрешение событий/местные шаги, фазовый дрейф и время расхождения. Контрольные случаи выбрать до новых результатов по хозяину/мере/типу исхода. Эксперименты со стартовыми возмущениями делать в нескольких направлениях/масштабах, не считать D–D′ бинарным тестом хаоса. Не вычислять долю всего ансамбля по этой адресной подвыборке.

**Готово:** таблица причин с уровнями уверенности и остающимися неизвестными; доступные балансы/диагностики действительно сохраняются; выбор D/T/hybrid обоснован не только скоростью. Не обязательно доказать механизм хаоса для каждой орбиты, если заявляется только распределительный допуск.

### OPT-15 — Спроектировать и зафиксировать P2-2b v2

**Приоритет:** перед новой независимой серией. **Зависимости:** OPT-12–14 и измерение стоимости OPT-19.

Горизонт 10000 лет. Прямые парные интервалы долей с границей 0.005; индивидуальная частота несовпадений остаётся отдельной диагностикой. Заранее определить уровни утверждений (смесь/хозяева/ячейки), категории, семейства одновременных сравнений, правило неизвестных исходов, физику/события, fixed N либо обоснованную последовательную процедуру. Мощность считать по фактической парной дисперсии и диапазонам возможного эффекта после fallback; проверить покрытие на неоднородных ячейках и редких категориях. Сводную стратифицированную сумму не объявлять буквально iid-биномиальной без обоснования применяемой границы. Не назначать 4–5 тыс. единиц заранее.

Новые seeds/единицы и freeze протокола до исходов. P2-2a и адресные разборы — development. Если требуемая точность недостижима, сужать научное утверждение явным решением, не считать inconclusive успехом и не ослаблять критерий после просмотра holdout.

**Готово:** воспроизводимый power/coverage расчёт, замороженный план, явный ресурсный запрос. Само обсуждение плана не разрешает аренду.

### OPT-16 — Вернуться к событиям и требованиям P3, не ограничиваться исходами D/T

**Приоритет:** до W1 production. **Зависимости:** изменённые backend/fallback OPT-10–12.

Сохранить отдельную проверку контакта между шагами/касания, временного выхода и возврата, завершения окна ухода, событий ровно на границе и переключении. Сравнить удвоенное разрешение. Проверить чувствительность к заранее заданным радиусу/окну operational_escape по W1-протоколу; не приписывать конечному окну вечный уход. Общие EscapeTracker/polynomial_contact для D и B означают, что одно совпадение методов не исключает общий дефект события.

**Готово:** V05 и требуемая часть P3 имеют новые доказательства для фактически выбранного режима. Старые аналитические контроли сохраняются; повторять только затронутые и необходимые регрессии.

## Пакет F. Checkpoint, исполнитель W1 и хранение

### OPT-17 — Развести физический restart и точный диагностический replay

**Приоритет:** до длинных новых серий. **Зависимости:** контракт OPT-03/06, адаптеры OPT-10/11.

Физический checkpoint содержит все тела/время/единицы/оси/физику/контракт/историю событий/диагностики; он может начинать новую адаптивную историю и проверяется по согласованным научным допускам. Native checkpoint нужен там, где требуется воспроизвести внутреннюю историю IAS15; отдельно проверять сериализацию REBOUNDx и совместимость ABI, не обещать побитовый restart заранее.

Сохранять периодически и при переключении/нарастающей проблеме; атомарная запись, контроль диска/размера, минимально достаточная частота по стоимости. Испытать внешнее убийство процесса и продолжение в другом процессе, не только штатный stop-file. Недопустимы потеря/дублирование конечных исходов и принятие checkpoint чужой версии. Это не основание разбивать каждую орбиту на множество коротких новых интеграций без проверки накопленного эффекта restart.

**Готово:** прерванный маршрут завершает тот же контракт без потери знаменателя; пределы эквивалентности и ограничения нативного replay опубликованы. Проверены выжившие, события и high-e.

### OPT-18 — Сквозной допуск через настоящий исполнитель W1

**Приоритет:** обязательный продукт перед W1. **Зависимости:** OPT-15–17 и положительные подтверждающие результаты.

Подключить выбранный backend через явный адаптер и manifest допуска с горизонтом, численным режимом, областью high-e, физикой и моделью событий. Freeze-guard должен отвергать несовместимые версии, а не принимать имя DOP853 как достаточный допуск. Малый полный маршрут: входы→генерация/замороженные units→интегрирование→событие/restart→исходы/веса→анализ/таблица с неопределённостью. Включить сквозной проверочный выпуск V09 и передачу продуктов по stage_handoff.

**Готово:** реальный W1 runner, не только исследовательский стенд, воспроизводит ограниченный пример и отклоняет неподтверждённый режим. P2-2b сама по себе не закрывает P3/W2.

## Пакет G. Измеренная оптимизация стоимости

### OPT-19 — Пересобрать модель стоимости по фактической работе и хвосту

**Приоритет:** перед размером/бюджетом новых длинных серий. **Зависимости:** после минимальной численной стабилизации.

Разделить CPU-часы, сумму wall-времён worker, календарное время, JIT/setup, ожидание, I/O, неуспешные прогоны и повторы. Страты: хозяин/мера/исход/период/момент fallback. Публиковать распределение длительности и самые долгие задания, а не только среднее. Калибровка D=0.77 относится к фактически просчитанной траектории; не умножать ей автоматически бюджет 10000-летнего W1. Цена high-e считается по времени/числу шагов, не по доле единиц.

**Готово:** прогноз объёма и критического пути с диапазоном неопределённости; валидирован на отдельной небольшой репрезентативной части. Пилот W1 оценивается отдельно от P2-2b.

### OPT-20 — Оптимизировать измеренные узкие места, не менять двигатель заранее

**Приоритет:** после корректности; реализация только по профилю. **Зависимости:** OPT-19.

Сначала проверить прогрев JIT/повторное использование compiled cache, расходы на один worker, регистрацию событий и I/O. Модельные длинные задания уже идут первыми: не продавать это как новую оптимизацию. Уточнить прогнозы длительности и баланс D/T/B, не отбрасывать дорогие задания по удобству. Число worker выбирать по физическим ядрам, cpu.max, памяти и измеренному SMT-эффекту. Не считать 64 vCPU равными 64 полноценным ядрам и не запускать новые локальные worker сверх configs/resources.yaml без явного профиля/согласования.

Не обещать полного заполнения 32 worker при одном длинном B: одна последовательная орбита не ускоряется количеством свободных процессов. Разбиение с checkpoint служит восстановлению и управлению сроками, а не бесплатному параллелизму. Пакетирование многих проб, GPU, иной интегратор, кэш внешнего поля — отдельные проверяемые альтернативы лишь при доказанном новом bottleneck.

**Готово:** измеренное ускорение полного маршрута при неизменных или заново проверенных научных критериях; нет ухудшения надёжности/хранения.

## Пакет H. Надёжность выполнения и доказательств

### OPT-21 — Устранить одиночную точку отказа supervisor

**Приоритет:** до следующей оплачиваемой серии; не блокирует короткие локальные тесты. **Зависимости:** контракт исполнения/ресурсов.

Сначала разобраться с доступными свидетельствами прекращения прежнего процесса; если причина невосстановима, явно это признать. Контролировать живость и фактическое продвижение задачи, не существование старого PID. Испытать падение supervisor, сеть/SSH timeout, завершение научного процесса с failed, sleep/reboot управляющего ПК, частичную выгрузку и повтор finish. Сделать операции завершения идемпотентными и ограниченными instance_id данной задачи; личную станцию пользователя не затрагивать.

Предложить пользователю конкретный резервный маршрут контроля срока/расходов. Секреты не помещать в run/журналы. Проверки максимально локальные/имитационные, без аренды ради каждого отказного теста.

**Готово:** fault-injection тесты и честный режим ручного контроля, если автономность не обеспечена. Ни запись в runtime, ни зелёные тесты сами по себе не означают работающую фоновую службу.

### OPT-22 — Сделать артефакты и утверждения прослеживаемыми без роста бюрократии

**Приоритет:** в каждом пакете и перед передачей этапа. **Зависимости:** нет.

В results/evidence/claims.csv добавить/уточнить главные ограниченные утверждения с run_id, проверками и пределами. У старых скриптов сохранять происхождение и не удалять исторические инструменты массово.

## Порядок реализации и точки остановки

1. **Первый ограниченный пакет:** OPT-01–05. Устранить подтверждённый дефект units и риск записи, привести проверки/сводки в порядок. Не менять силы, интегратор и исходы P2-2a.
2. **Входы и диагностика:** OPT-06–09, необходимая часть OPT-17. Получить корректные входы и доказательный replay/диагностику B. Не обещать фиксированное время нахождения причины.
3. **Численная стабилизация:** OPT-10–14, проверки событий OPT-16, остальная часть restart OPT-17. После каждого изменения режима новая версия и затронутые регрессии.
4. **Планирование подтверждения:** OPT-19, затем OPT-15. Параллельно по зависимости, но без запуска других агентов: локальные тесты supervisor OPT-21 и отчётность OPT-22. Чистая установка OPT-07 должна быть проверена до подтверждающего запуска.
5. **Подтверждение и передача:** отдельный согласованный расчёт P2-2b; далее OPT-18 и итог допуска. OPT-20 — только измеренные ускорения, которые не создают лишнюю повторную верификацию.

**Ворота G-A (безопасность):** подмена/несовместимый run отвергаются без записи, проверки сообщают правду.
**Ворота G-B (B):** первопричина малого шага установлена достаточно для обоснованного изменения, исходный случай/регрессии пройдены; либо явно ограничена область B.
**Ворота G-C (high-e):** проверенный fallback/сохранение состояния, учтён полный знаменатель и стоимость.
**Ворота G-D (новая серия):** режим/события/restart проверены, критерий/новые данные заморожены, бюджет измерен, необходимые расходы отдельно разрешены.
**Ворота G-E (W1):** положительная оценка выбранного допуска на нужном горизонте + P3/сквозной runner + manifest/handoff. При inconclusive — ворота не открывать.
