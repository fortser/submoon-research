## 5. Лимиты и безопасность исполнения

Это диагностические ограничения данного задания, а не измеренные оценки производительности.

- Один pytest/диагностический worker одновременно; без xdist. Нужные тесту дочерние процессы допустимы, но учитываются и ограничиваются.
- Соблюдать `configs/resources.yaml`: один поток, ≤2 GiB памяти для дерева диагностики, минимум 5 GiB свободного диска. Не утверждать наличие OS-квоты, если её нет; проверять доступными средствами и останавливать при превышении.
- Новые доказательства ≤256 MiB; большие временные каталоги/копии проекта не создавать.
- Проба executable/одиночный кандидат: внешний лимит **30 s**.
- Небольшой тестовый поднабор: **60 s**; целевой профиль warning — до **120 s**.
- Суммарное время исполнения диагностических subprocess в этой задаче: **≤600 s**. Время чтения/анализа сюда не включается. Записывать фактические затраты; не обнулять бюджет новым именем attempt.
- Не более одного повторения неизменного probe. Следующие запуски должны проверять различающее условие: другой executable, наличие предшествующего теста, режим capture и т. п. Изменение фиксировать до запуска.
- Один итоговый полный Windows pytest допускается **только после локализации и устранения причины либо доказательства безопасности**, с лимитом **180 s** и по-тестовым логом. Если уже видно, что корректный набор не укладывается, не запускать заведомо неполную серию: представить измерения и предложить отдельный бюджет.
- Платные действия, сеть, Vast API/CLI, аренда, облако, установка/обновление зависимостей, долгие научные серии запрещены. Наличие ключей и старого rental-файла ничего не разрешает.

### 5.1. Внешний timeout должен оставлять управляемые процессы

Нельзя полагаться только на timeout инструмента агента. При собственном harness:

- запускать subprocess списком аргументов, с явным cwd; `shell=False`, если shell не является непосредственно исследуемым executable;
- stdout/stderr писать в отдельные файлы текущей попытки, не накапливать неограниченно в памяти;
- фиксировать PID, время старта и доступные сведения о потомках;
- иметь внешний deadline и порядок остановки **только своего дерева**;
- на Windows допустим `taskkill /PID <свой_корневой_PID> /T /F` при проверенной принадлежности; запрещены `taskkill /IM python.exe`, `killall`, остановка всех bash/WSL и любые действия над чужими процессами;
- после timeout отдельно проверять остаточные процессы. Исчезновение pytest-родителя не доказывает завершение всех потомков;
- если Windows-процесс запускает WSL, Windows-дерево не доказывает очистку Linux-процессов. Не использовать `wsl --shutdown`. Без безопасного способа различить собственные процессы — не запускать такой probe, зафиксировать ограничение.

Если текущий harness не позволяет обеспечить ограничение/очистку, сначала подготовить узкую безопасную обёртку или остановиться с описанием ограничения. Не экспериментировать с неизвестным shell-сценарием.

### Шаг C. Локализация причины

Выбирать следующую ветвь по фактам:

| Наблюдение | Следующее ограниченное действие |
|---|---|
| Одиночный тест задерживается | Получить стек/процесс-потомок/точную команду; свести к безопасному минимальному вызову без исполнения rental-сценария |
| Отдельно проходит, после соседнего теста задерживается | Проверить короткую упорядоченную пару/поднабор; искать загрязнение окружения, cwd, monkeypatch, глобальных обработчиков |
| Все короткие группы быстры, общий бюджет исчерпан постепенно | Составить распределение durations; не объявлять deadlock. Холодный и тёплый старт фиксировать отдельно, кеши не удалять ради эксперимента |
| Есть живой потомок после окончания родителя | Сначала безопасно остановить своё дерево и сохранить доказательства; не запускать новые попытки поверх него |
| На Windows разрешается неожиданный `bash` | Проверить происхождение executable и аргументы, отличить проблему теста/окружения от научного кода; не править PATH глобально |
| Возникло обращение к сети/реальным ресурсам | Остановиться до вызова; изолировать только безопасным локальным тестовым mock либо передать проблему, не использовать реальные credentials |
| Причина уходит в численные методы/события/физический restart | Не исправлять. Собрать минимальные доказательства и эскалировать |

Для причинного вывода желательно сравнение, где меняется **один фактор**. Например, явно выбранный проверенный shell против прежнего разрешения пути. Одно исчезновение симптома после случайного изменения недостаточно. Не требуется обязательно воспроизвести опасный или зависающий вариант повторно, если это нарушает ограничения: тогда сузить силу вывода.


Smoke создаёт **новый** L0 run; он не закрывает W2. Если времени на проверку не осталось, честно перечислить невыполненное, не ссылаться на старый PASS как на текущий.

6. Если исправление платформенное, WSL-проверка — дополнительная, не замена Windows-воспроизведению. Только Ubuntu-24.04, указанный Python, по одному ограниченному процессу, без установки пакетов.
7. Один полный Windows pytest — только по условиям §5. Пример аргументов: `-m pytest -vv -rA --tb=long --durations=30`; сохранить start/finish каждого доступного этапа и общий returncode. Не запускать полный WSL набор автоматически.

## 7. Инструментирование и обязательные артефакты

Предпочесть существующие средства pytest. Новый helper писать только если без него нельзя получить deadline/логи/безопасную очистку. Научную логику в helper не добавлять.

Для **каждой попытки** отдельная запись, минимум:

```json
{
  "attempt_id": "c120-<UTC>-01",
  "purpose": "какую гипотезу различает",
  "argv": ["точный executable", "аргументы"],
  "cwd": "корень проекта",
  "started_utc": "фактическое время",
  "elapsed_seconds": null,
  "timeout_seconds": 30,
  "returncode": null,
  "timed_out": false,
  "root_pid": null,
  "child_processes_observed": [],
  "cleanup_status": "not_checked",
  "stdout_path": "относительный путь",
  "stderr_path": "относительный путь",
  "changed_factor": null
}
```

Это шаблон, не готовые результаты: заменить поля фактами, неизвестное оставить `null`/`not_checked`. Не печатать токены, секреты и произвольные чужие command line. Реальный returncode после принудительного завершения хранить отдельно от признака timeout.

Минимальная структура нового evidence-каталога:

- `environment.json`, `git_status_before.txt`, SHA исходных релевантных файлов;
- свежая collection и сравнение с исторической;
- `attempts.jsonl` или эквивалентный машинный реестр;
- stdout/stderr каждой попытки, доступные стеки и сведения о собственных процессах;
- `diagnosis.json`: подтверждённые наблюдения, гипотезы, вывод, его ограничения, расход бюджета;
- при патче — diff, регрессии, коды завершения проверок;
- manifest с SHA проверенных исходников/тестов/логов, временем и статусами; не включать секреты;
- итоговый отчёт `reports/analysis/W2_T072_C120_<UTC>.md`.

Не называть пустой лог доказательством отсутствия ошибок. Не считать завершение log writer завершением тестового процесса. При использовании shell pipeline отдельно сохранить exit status pytest: успешный `tee` не означает успешный pytest.

## 8. Критерии завершения и передачи

### Вариант A — причина локализована

Необходимо:

- точный тест/операция или измеренный механизм исчерпания бюджета;
- воспроизводимые команды, фактические логи/время/процессы;
- отделение подтверждённого механизма от гипотез;
- если патч применён — разрешённая область, сохранённая гарантия теста, положительная и отрицательная регрессии;
- проверенная очистка своих процессов либо явное неразрешённое ограничение;
- отсутствие изменений защищённых файлов;
- отчёт, manifest и обновлённый трекер.

Диагностическую T072 можно завершить с узким результатом, даже если для общей регрессии нужен отдельный обоснованный бюджет/дальнейший патч. Но **общий pytest нельзя объявлять passed без полного завершённого запуска**. Отдельный тест не заменяет весь набор.

### Вариант B — данных недостаточно или нужен выход за полномочия

Остановиться в пределах бюджета. Зафиксировать `inconclusive`, что исключено/не исключено, минимальный воспроизводимый пример и **один** следующий различающий шаг. T072 оставить `ready` для конкретного продолжения или `blocked` с объяснённой внешней предпосылкой. Не выдавать задачу за полностью решённую.

### Трекинг

- Создать новые check/result/issue при необходимости с фактическими refs и свободными ID из свежего состояния. Не занимать заранее предполагаемый номер C121/R038 без проверки.
- Исторический C120 не переписывать в «всегда был passed». Новую законченную проверку связать через related_ids и явно указать её область.
- Обновить T072, освободить active-владение; обновить W2-STAGE/следующий шаг только через `track add`, сохраняя остальные поля/refs. Фактическая revision каждый раз обязательна.
- Не закрывать T070, I044, C117, F3/F4/F5, ворота W1/W3 или научный допуск.
- Если появляется главное новое утверждение о причине/исправлении, добавить отдельную строку в `results/evidence/claims.csv` с доказательствами и ограничениями, не переписывая прежние.
- В финале повторить `project.py validate`. STATE/PLAN/DECISIONS/SUMMARY вручную не править. PROJECT_MAP.md не менять.

## 9. Формат ответа пользователю

Кратко, но конкретно:

1. Что именно задерживалось и насколько надёжно установлена причина.
2. Что изменено (пути) либо почему патч не нужен/не разрешён.
3. Какие проверки завершились и их числа; какие остались неполными.
4. Есть ли оставшиеся собственные процессы.
5. Ссылка на отчёт, evidence ID, записи трекера.
6. Следующее одно действие; не начинать F3/F4/F5 без нового поручения.

**Не обещать научную корректность по результатам этой технической работы.** Если потребуется разбор сложной гонки, семантики физического checkpoint или изменение научных предпосылок — явно попросить возврат к сильной модели, приложив минимальные доказательства. Не запускать другую модель самостоятельно.
