# Универсальный протокол трекинга

Версия 1.0. Одинаков для Codex и любого другого агента, CLI, IDE или человека. Используются UTF-8 Markdown, YAML и JSONL. Никакого обязательного внутреннего memory API harness.

## Четыре уровня чтения

| Уровень | Что читать | Когда |
|---|---|---|
| 0: правила | AGENTS.md | В начале новой сессии; если harness не читает автоматически — передать явно |
| 1: весь проект | STATE.md и при необходимости PLAN.md | Узнать текущую фазу, зависимости и ближайший шаг |
| 2: этап | tracking/stages/W0/SUMMARY.md | Понять активные задачи, препятствия и последние значимые исходы |
| 2а: научная постановка | docs/context/project_overview.md → docs/stages/Wn.md и его required reading | При входе в научный этап: общая цель, полный раздел этапа, входы, шаги и критерии |
| 3: доказательства | RECORDS.md → конкретные refs/detail_path/run_id | При реализации, проверке или разборе причины решения |

Полный журнал и `tracking/index.json` не загружать в контекст по умолчанию. SUMMARY ограничивает число показываемых записей; RECORDS содержит текущие версии всех записей, journal — всю историю. Полный текст статьи и огромные траектории загружаются только для нужного вопроса.

Полную программу не читать при каждом запуске: полные разделы распределены по досье и общим блокам с SHA исходника. `python scripts/build_stage_briefs.py --check` выявляет устаревание. Нужные первичные статьи и продукты предыдущих этапов читаются отдельно; досье содержит постановку, не доказательства выполненных расчётов.

Очередность и правила обратной связи: [RESEARCH_ROADMAP.md](../RESEARCH_ROADMAP.md). Перед переходом передавать версии входных продуктов и критерии приёмки, связывая результаты предшественника и задачу получателя через related_ids. Новые научные этапы добавляются отдельным решением без перенумерации старых ID.

## Источники истины

- `tracking/project.yaml`: структура этапов, зависимости, ворота готовности, focus_stage. Меняется редко, изменению соответствует решение в журнале.
- `tracking/stages/<stage>/journal.jsonl`: единственный источник изменяемого состояния записей этапа. Одна строка — новая полная версия одной короткой записи, с UTC, actor и последовательным revision. История логически дополняется; старые строки не исправляются.
- `STATE.md`, `PLAN.md`, `DECISIONS.md`, `SUMMARY.md`, `RECORDS.md`, `tracking/index.json`: производные представления, автоматически обновляются после `track add`; восстановление — `track render`.
- `docs/tasks`, `docs/predictions`, `reports`, `runs`: подробности постановки и доказательства. Карточка задачи хранит требования; текущий статус берётся из журнала. Большой отчёт не копируется в журнал.
- `tracking/runtime.json`: только действующие внешние процессы (run_id, PID/job_id, хост, статус проверки, last_checked_utc, команда остановки, логи, лимиты). Пустой список означает отсутствие зарегистрированных процессов, а не автоматическую проверку всей ОС.

Исходная научная программа и организационный проект — требования; текущие статусы из них не выводить. Прежний развёрнутый план старта сохранён в `docs/roadmap.md`, начальные основания решений — в `docs/bootstrap_decisions.md`.

## Что считать прогрессом

Проект: какие научные продукты готовы, какие ворота закрыты, какой этап находится на критическом пути, какие ограничения препятствуют следующему выводу. Не вычислять общий процент по числу файлов, задач или интеграций.

Этап: активная задача, полученный продукт, проверка, незакрытая неопределённость и следующий конкретный шаг. Для расчётной серии допустимы counts planned/running/completed/failed/partial, но это прогресс исполнения, не процент научной готовности.

Каждый этап имеет одну запись `<stage>-STAGE`. Статусы: planned → ready → active → complete; blocked при конкретной невыполненной предпосылке. Возможен возврат к active после найденной ошибки: добавить событие с причиной и affected_runs, пересмотреть зависимые выводы. Completion требует refs на проверенные продукты; закрытие ворот всё равно требует научного рассмотрения, наличие ссылки само по себе не доказывает качество.

## Виды записей и жизненный цикл

| Вид / ID | Что фиксировать | Статусы |
|---|---|---|
| task / W0-T001 | Конкретный результат, исполнитель, вход, следующий шаг | planned, ready, active, blocked, done, cancelled |
| decision / W0-D001 | Вопрос, выбранный вариант, отвергнутые альтернативы, причина и условие пересмотра | proposed, accepted, rejected, superseded |
| check / W2-C001 | Метод, заранее выбранный критерий, команда/версия и фактический результат | planned, passed, failed, inconclusive |
| result / W3-R001 | Измеренное утверждение, единицы/мера/горизонт, uncertainty, run_id и ограничения | preliminary, validated, rejected, superseded |
| issue / W2-B001 | Симптом, причина, область влияния, исправление, независимая повторная проверка | open, investigating, fixed, verified, dismissed |
| hypothesis / W1-H001 | Гипотеза и альтернатива, различающее предсказание, критерии и исход | proposed, testing, supported, contradicted, inconclusive |
| plan / W0-P001 | Следующая последовательность задач, основания приоритета, зависимости и условие пересмотра | proposed, active, completed, superseded |

Исправлена (`fixed`) ≠ проверена (`verified`); выполнен расчёт ≠ validated result; отвергнутое решение и опровергнутая гипотеза сохраняются. `related_ids` связывает ошибку, исправление, проверку и пересмотр результата. `supersedes` указывает заменяемую запись; `affected_runs` перечисляет затронутые запуски. Для крупных цепочек подробности вынести в отдельный Markdown и указать detail_path.

Статусы evidence-bearing (passed/failed check, validated result, fixed/verified issue, supported/contradicted hypothesis, done task, complete stage) требуют существующих локальных refs. Автомат проверяет структуру и наличие файлов; научную достаточность и независимость проверки оценивает агент по протоколу верификации.

## Размер и частота записей

Одна запись — один содержательный факт: заголовок ≤160 символов, summary ≤1200, next_action ≤500. Предпочтительно summary из 2–4 предложений: что сделано/узнано, почему важно, ограничение. Не хранить рассуждения диалога, полный stdout или каждый промежуточный shell-вызов.

Обновлять после завершённой задачи, принятого/отвергнутого решения, проверки, нового результата, найденной/исправленной ошибки, изменения гипотезы/приоритета, перед долгим запуском и перед передачей сессии. Сводка этапа должна отражать реальность к завершению сессии.

## Запись из любого harness

1. Прочитать SUMMARY и revision этапа; при работе взять задачу переводом в active с конкретным owner.
2. Создать короткий JSON по `tracking/record.example.json`. Для обновления сохранить тот же ID и весь текущий набор полей. Подготовить отчёт/доказательство до статуса, требующего refs.
3. Выполнить из корня:

```powershell
.\.venv\Scripts\python.exe scripts/project.py track show --stage W0
.\.venv\Scripts\python.exe scripts/project.py track add --stage W0 --input scratch/record.json --actor codex-main --expected-revision 2
.\.venv\Scripts\python.exe scripts/project.py track render
```

Число 2 — пример; подставлять фактически прочитанный revision. Конфликт означает, что состояние изменилось: прочитать его и согласовать изменение. Не повторять запись вслепую с новым номером.

`track show --stage W0 --full` выдаёт все текущие записи этапа в JSON; `--id W0-T001` выбирает одну запись. Журнал содержит автора и предыдущие состояния. Команда после успешной записи автоматически обновляет сводки; отдельный render нужен после ручной правки project.yaml или восстановления.

## Совместная работа

Единый глобальный lock предотвращает одновременную запись и рендер; expected_revision предотвращает потерю уже внесённых изменений. Запись active-task с другим owner отклоняется до освобождения задачи текущим владельцем. Агентам поручать разные файлы/задачи; lock журнала не защищает исходный код от одновременной правки. Автоматического истечения владения нет: перенос фиксировать после выяснения статуса предыдущего исполнителя.

При сбое во время записи журнал заменяется атомарно; сводки можно восстановить render. Если остался `.write.lock`, прочитать его, проверить PID/хост и только после подтверждения отсутствия писателя удалить этот конкретный lock. Не удалять историю. Для разных клонов Git нужна координация через основного агента: файловый lock действует только в общем каталоге, слияние двух журналов нельзя считать автоматически разрешённым.

Ни один файл не обновляется сам от факта работы агента. Автоматическая часть — проверка и построение сводок после зарегистрированного события; обязанность записать событие лежит на исполняющем агенте и закреплена в AGENTS.md.
