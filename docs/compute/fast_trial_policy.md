# Быстрый аппаратный тест по сообщению пользователя — W2-D043

Принято 23.10.2026. Источник: пользователь прямо установил, что сообщение «сканер нашёл подходящую рабочую станцию» (или равнозначное) автоматически означает разрешение на её поиск, аренду и проверку технических характеристик. Повторно спрашивать «арендовать?» в пределах этого протокола нельзя.

## Границы разрешения

- **Триггер — новое явное сообщение пользователя о находке**, не звук/строка радара, не каждый цикл сканирования и не этот разговор об изменении правил. Монитор остаётся read-only.
- Одно сообщение разрешает **один новый on-demand контракт для аппаратного теста**; одна попытка create, без слепых повторов при неоднозначном ответе. Сигнал и его расходование сохраняются под уникальным `signal_id`/`run_id`; перечитывание сообщения, рестарт и пересмена агента не создают нового разрешения. Дубликат сообщения о той же находке не расходуется второй раз без прямого указания пользователя на новую попытку.
- Это постоянный порядок для будущих сообщений, **не прежний однократный token W2-D031 на всё время**. Старые approval/attempts сохраняются. Отдельные новые явные поручения могут задавать другие границы.
- Семейство — профиль радара `p2_2a_station`: verified/unverified, amd64, вычислительный resource_type, ≥64 эффективных vCPU, ≥95% CPU хоста, RAM ≥64 GB, 60 GB диска, reliability ≥0.97, SSH-порт, ≥28 модельных физических worker. 9975WX ≤$0.65/ч; аналоги ≤$0.75/ч с диском и действующие прогнозные ограничения радара. Исключённые машины не возвращаются автоматически.
- **До 30 минут от начала create и до $1 за один сигнал**, включая диск и трафик; только малый диагностический пакет, ≤10 MB upload и ≤10 MB download. Если цена/трафик неизвестны или превышают лимит — не создавать контракт. Ни лимит YAML, ни большой баланс не расширяют согласие.
- Основной научный прогон, B144, spot, новые тома, платные повторы и продолжение сверх срока/бюджета не разрешены. Они требуют отдельного согласия. Запрещено превращать этот порядок в автономную скупку сигналов.
- После теста выгрузить малую диагностику с SHA и удалить **только свой** временный инстанс, проверить отсутствие. При раннем отказе не ждать 30 минут. Отмена обязательного watchdog по W2-D032 сохраняется; однако срок/бюджет действуют независимо от наличия ответа пользователя. Продолжение по молчанию запрещено.

## Как убрать задержку

### Заранее, без ожидания сигнала

1. Иметь готовые исполнитель, probe, тесты, образ и шаблон манифеста. Проверить CLI/SSH-ключ/зависимости и обработку ошибок. Не писать скрипт аренды с нуля после сигнала.
2. Поддерживать работоспособный радар и сохранённые кандидаты. Готовность окружения — отдельный снимок, не гарантия будущей доступности аккаунта/API.
3. После изменения кода прогнать офлайн-тесты. Полный pytest/научный аудит не входит в критический путь каждой аппаратной аренды.

### После сообщения пользователя

1. В уже начатой сессии не повторять изучение всей документации. В новой — прочитать STATE, SUMMARY и этот компактный протокол; сведения об остальных научных этапах для аппаратного теста не нужны. Взять задачу в active, записать `signal_id`, исходное сообщение и W2-D043. Небольшая локальная запись не заменяется большим отчётом до create.
2. Прочитать находку и UTC. **Не запускать полный поиск рынка**, если есть конкретный кандидат. Непосредственно перепроверить точный offer/machine через актуальный API; проверить цену с 60 GB, ресурс, статус, трафик, бюджет и отсутствие своего незавершённого контракта. Проверки аккаунта и оффера по возможности выполнять параллельно.
3. Если gates пройдены — **сразу один create**, без промежуточного запроса согласия, подготовки нового скрипта, повторного полного pytest или оформления развёрнутого отчёта. Самая короткая цепочка: `кандидат → свежая проверка → запись попытки → create`.
4. Сразу сохранить очищенный ответ create: UTC, HTTP-статус, success/new_contract или безопасный код ошибки. Секреты/полное тело ответа и traceback с URL не печатать. При timeout/неоднозначности искать контракт по уникальной label, **не повторять create**. Отсутствие в одном inventory или аудите не является доказательством того, что запрос не принят.
5. После получения ID — runtime, SSH, topology/affinity/cgroup, доступная RAM, нагрузка, ограниченная проверка памяти и диска. Честно отделять физические ядра от потоков, видимую RAM от cgroup-лимита, краткий тест от полной проверки всей памяти/эксклюзивности.
6. Выгрузка → SHA → destroy → подтверждение → короткий отчёт и записи результата. Большой отчёт пишется **после** освобождения ресурса. При проблемах API приоритет — восстановление контроля расходов, а не документация.

## Время и доступность

Цель — убрать минуты подготовки из критического пути. Время чтения/решения агента и сетевой задержки не гарантированы; «аренда за N секунд» не объявляется измеренным результатом без реального бенчмарка. Create может отказать даже после свежего rentable=true: радар не резервирует предложение. Недоступность не доказывает, что его забрал другой клиент.

Новый отказ после расходования попытки не даёт права бесконечно пробовать другие машины. При неподходящей цене/характеристиках объяснить конкретное отклонение без запроса согласовать то, что уже разрешено.
