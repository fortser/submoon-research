# Быстрый аппаратный исполнитель W2-D043

Код: `scripts/vast_hardware_trial.py`, `src/submoon_research/compute/hardware_trial.py`, `trial_transport.py`; отдельный Linux probe — `scripts/vast_hardware_probe.py`. Научный код/данные на станцию не загружаются. Радар этот исполнитель не импортирует и не запускает.

Разрешение: [fast_trial_policy.md](fast_trial_policy.md). **Только новое сообщение пользователя о находке разрешает run**. Команды `prepare`, `--help`, разработка и эта инструкция сами по себе не разрешают аренду. Один сигнал — один create; перезапуск не восстанавливает token. В программном коде невозможно доказать человеческое происхождение сообщения: корректность `source_ref`, `user_message` и `episode_id` — ответственность оператора, а не результата радара.

## 1. Заранее: prepare без сети и расходов

Из корня с Python проекта:

```powershell
.venv/Scripts/python.exe scripts/vast_hardware_trial.py prepare
```

Возвращается относительный путь уникального JSON в `data/interim/vast_trials/prepared/`. Сохраняются версии Python/Paramiko/requests, SHA кода и gates, fingerprint публичной части SSH-ключа, наличие источника авторизации. **Сеть, create, нагрузка и чтение API-ключа не выполняются.** CLI Vast.ai только отмечается как доступный/нет; для исполнения используется REST, а не CLI create. Зависимости уже должны быть установлены; для новой среды extra — `hardware_trial` из `pyproject.toml`, установка выполняется заранее, не на критическом пути и не на арендованной машине.

По умолчанию SSH-ключ — `~/.ssh/vast_agent`. Для другого ключа глобальный параметр ставить **до** подкоманды:

```powershell
.venv/Scripts/python.exe scripts/vast_hardware_trial.py --ssh-key <путь> prepare
```

Приватный ключ не копируется в проект/манифест/на сервер. Перед первым платным использованием публичный ключ должен уже быть зарегистрирован в Vast.ai; prepare не выполняет его регистрацию и не проверяет аккаунт через сеть. Ключ API при run берётся из `VAST_API_KEY` либо штатного файла CLI, не передаётся в argv и не попадает на станцию.

Изменение кода/gates, Python, зависимостей или ключа требует нового prepare. Старые snapshots не перезаписываются. Снимок не обещает будущую доступность API/оффера; это не научный или аппаратный допуск.

## 2. После нового сообщения пользователя

1. Взять конкретную аппаратную задачу W2 в active с уникальным owner; отдельное решение о согласии не нужно — действует W2-D043.
2. Выбрать конкретный offer/machine по находке, не делать полный sweep. Создать небольшой UTF-8 signal JSON на основе `hardware_signal.example.json`.
3. `source_ref` — стабильная ссылка/ID **реального сообщения пользователя**, не случайный timestamp. `episode_id` — стабильный ID эпизода/уведомления радара (одинаковый при смене offer_id той же находки), не ID каждого цикла. Дублирующее сообщение о той же находке не даёт второй попытки. Записать фактическое сообщение и поставить `user_found_station: true` только по его реальному наличию. Не превращать обсуждение правил/«приступай к разработке» в сигнал аренды.
4. Запустить один подготовленный маршрут:

```powershell
.venv/Scripts/python.exe scripts/vast_hardware_trial.py run --prepared <подготовленный.json> --signal <сигнал.json>
```

Пример поставляется с `user_found_station=false` и синтетическими ID, поэтому его нельзя случайно использовать как разрешение. Никаких новых вопросов «арендовать?» в пределах уже разрешённого протокола.

### Что делает run

- Проверяет активную задачу/owner, подготовленный снимок и уникальность source/episode. OS-lock не допускает двух параллельных исполнителей на этом workspace; exclusive/fsync claim-файлы переживают перезапуск. Сбой между двумя claim блокирует повтор консервативно. **Не удалять claims и не переносить исполнение в другой независимый клон для обхода ограничения.** Координация нескольких клонов/компьютеров — на операторе; локальный lock не является распределённым.
- Параллельно получает состояние аккаунта и **один свежий точечный** запрос оффера. Использует `radar.assess` и дополнительные фиксированные gates: amd64, verified/unverified, вычислительный контракт, ≥64 effective vCPU, ≥95% хоста, RAM ≥64 GB, reliability ≥0.97, SSH-порт, ≥28 модельных worker и прежние прогнозные ограничения. Machine 139652 остаётся исключённой.
- Проверяет 60 GB диска, цену base+storage и согласие с API total (допуск 1e-6), ≤$0.65/ч для 9975WX / ≤$0.75/ч аналогам; известные тарифы трафика **≤$0.02/GB** в каждую сторону (консервативный gate прежних контроллеров). Полный предел $1; без spot, томов, больших uploads, pip/apt установки. Старая проверка оффера старше 30 с не принимается.
- Сохраняет token, начало и 30-минутный дедлайн **до** единственного PUT create. HTTP create не повторяется. Authorization — заголовок, не URL/argv. Сохраняются только HTTP status, безопасный код, success и new_contract; полные ответы с instance_api_key не журналируются.
- REST и SSH выполняются в завершаемых дочерних процессах с wall timeout. Это защищает от зависшего сетевого потока, но **не является независимым внешним watchdog** на случай выключения ПК/гибели самого контроллера.
- При неизвестном ответе ищет свою уникальную label до резерва завершения; не считает один пустой inventory доказательством отсутствия контракта и не делает повторный create. Поздно появившийся контракт подхватывается. Явный структурированный отказ и отсутствие label — `create_refused`; timeout без установленного исхода — `needs_attention` с runtime-записью даже при неизвестном instance_id.
- Ждёт running с резервом: provisioning до последних 10 минут, probe максимум 300 с (удалённый скрипт timeout 230 с), минимум 180 с на завершение. Дедлайн контролируется по monotonic и UTC; при восстановлении срок не продлевается. Реестр — `tracking/runtime.json`, включает PID, label, ID/неизвестность, предел и команду recovery.
- SSH — к endpoint из авторизованного API, TOFU в отдельном known_hosts. В собственном временном контейнере отключает auto-tmux, создаёт уникальный каталог без перезаписи существующего. Передаёт только probe, сверяет upload SHA, выгружает ограниченный JSON и сверяет SHA. Непроверенный shell stderr не сохраняется: он может содержать секреты.
- Затем **при любом исходе** пытается удалить только подтверждённый свой instance_id/label/machine. Ошибка записи доказательств/реестра не должна препятствовать DELETE. Идемпотентный DELETE может повторяться, create — никогда. Перед выводом «удалён» нужны подтверждение DELETE либо явный 404/410 и разнесённые проверки inventory; при расхождении личности ресурс не удаляется вслепую. Финальная сверка счетов — только snapshot, возможны задержки начислений.

## 3. Что именно проверяется

- CPU model, affinity, topology физических ядер/потоков, видимые cgroup CPU/RAM limits, MemTotal.
- По 4 с нагрузки одного CPU, по 30 с на физических и логических CPU (ограничения: до 96 физических и 192 логических worker). Сохраняются per-worker CPU/wall и cgroup throttling. Sanity gate delivered CPU capacity ≥85% числа **тестированных** worker, не гарантия производительности научного кода.
- 512 MiB выделенной памяти с записью/чтением одного байта на страницу — **не полная проверка 512 MiB или всей RAM**.
- 64 MiB файла с fsync и сверкой SHA; чтение может быть cached. df/disk_usage относятся к файловой системе хоста, **не доказывают контрактную дисковую quota**.
- GPU — только inventory, без VRAM/stress test.

Видимые ресурсы сравниваются с заявленными отдельно от успешной нагрузки. Квота 61.44 вместо 64 vCPU — расхождение, не «совпало». Неизвестное остаётся null. Для сравнения доступного RAM cap с API принят явный **операционный допуск 1%** на округление/резервирование; он не научная оценка неопределённости. Родительские cgroup могут быть скрыты; короткий тест не доказывает эксклюзивность хоста или долговременную устойчивость. Результат не является W2/W1 научным GO.

## 4. Результат и восстановление

Артефакты: `data/interim/vast_trials/submoon-hw-<source_hash>/`. `manifest.json` — текущее состояние; `event-*.json` — неизменяемые последовательные snapshots, плюс очищенный create receipt, hardware.json, transfer/SHA и billing snapshot. Claims и журналы сохранять; завершённый запуск не перезаписывать.

Код выхода 0 — probe и сравнение видимых ресурсов прошли, удаление подтверждено, нет отмеченных сбоев реестра/доказательств. Код 2 — отказ, расхождение, недостаточность или необходимость вмешательства; даже `destroyed_verified` может иметь error_code о неудачном тесте. Само слово «удалён» не означает, что характеристики прошли проверку.

Если `needs_attention`, контроллер убит или ПК выключался:

```powershell
.venv/Scripts/python.exe scripts/vast_hardware_trial.py recover --run-id submoon-hw-<source_hash>
```

`recover` **никогда не вызывает create и не повторяет нагрузку**: сверка label → известный свой ID → удаление/проверка. Может работать после изменения кода без старого prepare, чтобы исправление программы не мешало прекращению расходов. При недоступном API остаётся необходимость ручного вмешательства в аккаунте; не обещать гарантированное прекращение платежей одним JSON-лимитом. Остаток runtime не удалять вручную, пока судьба контракта не выяснена. Новые run блокируются при незавершённом trial.

Запуск под наблюдением оператора должен иметь внешний tool timeout с запасом >30 минут (например, 1900 с); закрытие чата не создаёт автономного арендатора. Полный отчёт/трек результатов оформлять после освобождения ресурса, не до create.

## Ограничение приёмки

В W2-T056 проверяются офлайн-фейки и реальный локальный prepare. Полный новый REST/SSH путь на оплачиваемом инстансе ещё не пройден; API/образ могут измениться. Его первый живой контроль допускается следующим новым пользовательским сигналом W2-D043, без пересогласования в прежних пределах. Фактическое время от пользовательской команды до create пока не измерено; `runner_precreate_seconds` измеряет только внутренний участок исполнителя, не время чтения/рассуждений агента.
