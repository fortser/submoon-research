## Порядок выполнения

Отдельные локальные рабочие файлы и удалённая папка с instance_id. Прежние approval/attempts/bundle не перезаписываются. До upload — инвентаризация папки/процессов; переданные файлы проверяются по SHA-256. Зафиксировать код, окружение, конфиг и абсолютные сроки.

Установка → REBOUND/REBOUNDx, серверные pytest/Ruff и hardware gates → baseline → неизменённый baseline_gate с запасом 1.15 и фактическим остатком времени → полный стенд только при GO. Отказ любого обязательного gate ведёт к выгрузке доступной диагностики и удалению, без платной замены и обхода проверки. Долгие scientific jobs ограничиваются абсолютным сроком самим стендом.

Локальный отдельный supervisor контролирует этап/бюджет, после done/FAILED выгружает результаты с SHA-256, затем вызывает destroy и проверяет отсутствие контракта. При приближении срока останавливает задания, затем выгружает/удаляет. Это **не** отменённое правило «нет ответа за 30 минут → destroy»; подтверждение продолжения уже получено. Локальный supervisor не переживает выключение/сон/потерю сети ПК; независимый watchdog пользователь отменил W2-D032. Не обещать гарантированное соблюдение дедлайна при недоступном локальном исполнителе или API. На сервер не передавать API-ключ аккаунта. При сбое выгрузки повторять в пределах согласованного резерва; сообщать об угрозе лимиту, не оставлять ресурс без контроля молча.
