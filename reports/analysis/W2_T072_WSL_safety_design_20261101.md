# W2-T072: граница безопасной идентификации WSL-потомков

Дата: 01.11.2026. Исполнитель `pi-c120-20261101T095541Z`. Это статический анализ C121, новых диагностических процессов и научных запусков нет.

## Что можно утверждать по сохранённым данным

В `results/evidence/W2_T072_C120_20261101T095152Z/attempts.jsonl` перечислены Windows PID/имена, замеченные `psutil.Process.children(recursive=True)` во время короткой пробы, и факт отсутствия этих наблюдавшихся PID с прежним временем создания после возврата. Файл **не сохраняет ребра parent-child, command line, время отдельного наблюдения, дистрибутив WSL, Linux PID или содержимое `/proc`**. Поэтому по нему нельзя доказать, что именно `bash.exe` запустил `wsl.exe`, что конкретный Linux-процесс относился к тесту, или что он завершился. Наличие Windows `wslhost.exe` не идентифицирует конкретный Linux-процесс. Нельзя по этому списку безопасно находить и завершать произвольный процесс в WSL задним числом.

Дополнительно: русские значения `purpose` и `changed_factor` в сохранённом JSONL превратились в символы замены при записи; точные argv, времена, PID и статусы читаемы. Исправлять старое доказательство нельзя. Для будущих helper файлового логирования следует явно устанавливать UTF-8 и проверять round-trip.

Статически прочитаны `tests/unit/test_vast_p2_2a.py`, начальный импорт `scripts/vast_p2.py`/`scripts/vast_w2.py`, `_workers`, `_start_script` и `_start_script_p2_2a`. Проверяемый тест вызывает `bash -n` для анализа генерируемого текста; исследованный путь генерации не запускает этот текст. Причина появления WSL в наблюдаемом Windows-дереве **по статическому коду не установлена**. Все выводы C121 остаются ограниченными; кандидату нельзя приписывать исторический timeout.

## Возможный управляемый дизайн, не готовая гарантия

Для **намеренно запускаемой нами** Linux-команды можно проектировать WSL-wrapper с уникальным непредсказуемым attempt token, явным `Ubuntu-24.04`, отдельной session/process group, протоколом подтверждения `(token, boot_id, pid, starttime, pgid)` и deadline/watchdog **внутри Linux**. Проверка перед сигналом должна повторно сверять идентичность (PID может переиспользоваться), принадлежность группе и token; завершать только группу собственной попытки, без `wsl --shutdown`, и получать подтверждение после завершения.

Такой wrapper **не покрывает автоматически** случайный/неуправляемый `wsl.exe`, который внутренне запускает уже существующий Windows pytest/test/bash. Перед повторением исходного теста необходимо отдельно доказать, что вся его потенциальная WSL-ветвь действительно принудительно проходит через контролируемую точку создания и не может обойти wrapper. Одна переменная окружения, `WSLENV`, отдельная Windows Job Object или наблюдение Windows parent PID без проверки Linux-стороны сами по себе этого не гарантируют. Указывать distribution по умолчанию вместо фактической также нельзя.

Это **проект**, не реализованный watchdog и не пройденный тест безопасности. Эту границу нельзя считать разрешением для повторного запуска потенциально опасной пробы. Возможная альтернатива — подтвердить происхождение `wsl.exe` и доказать его отсутствие в тесте через контролируемое локальное окружение, не скрывая при этом проверяемую ветвь `bash -n`; влияние на воспроизводимость необходимо явно измерить. Такие действия требуют отдельного исполняемого безопасного протокола, а не изменения PATH системы или остановки чужих процессов.

## Статус

Причина C120 неизвестна. Новых тестов, исправлений, аренды и уборки процессов не выполнялось. Ни один существующий scientific/runner/test файл не изменён. Следующий шаг — согласовать/разработать протокол наблюдения и ограничения реальной Windows→WSL ветви с проверкой на собственных безвредных процессах **до** повтора pytest; если нельзя гарантировать её перехват, сохранить unresolved и не выполнять потенциально опасный probe. F3–F5 и научный runner не включены в этот шаг.
