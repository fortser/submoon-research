# W2-T072: найдено и исправлено расхождение Windows lookup; общий timeout остаётся открытым

Дата: 01.11.2026 UTC. Owner `pi-c120-resolution-20261101T183920Z`.
Evidence ID: `W2-T072-resolution-20261101T183920Z` — технические проверки, не научная серия.

## 1. Результат

**Подтверждён конкретный дефект в трёх инфраструктурных тестах:** проверяется наличие одного bash через `shutil.which`, но затем bare-name вызов Windows CreateProcess выбирает другой executable.

| Вызов в текущем Windows Python 3.10.6 | Фактически выбранный образ |
|---|---|
| `shutil.which('bash')` | `C:\Program Files\Git\usr\bin\bash.EXE` |
| `Popen(['bash', '-n'], ...)` | **`C:\Windows\System32\bash.exe`** |
| `Popen([найденный_абсолютный_путь, '-n'], ...)` | `C:\Program Files\Git\usr\bin\bash.exe` |

Это не предположение по имени процесса: оба образа измерены через `QueryFullProcessImageNameW`, процессы созданы с `CREATE_SUSPENDED=0x4` и завершены **без возобновления начального потока**. Их startup-код не выполнялся; эта проверка не запускала WSL. Метаданные системного файла: **Microsoft Bash Launcher**, версия 10.0.19041.1. Полные аргументы, PID, выбранные образы и завершение — `suspended_resolution.json`; метаданные — `system_bash_metadata.json`.

Причина расхождения — разные правила поиска: `shutil.which` использует поиск по PATH, а bare-name `CreateProcess` на Windows учитывает в том числе системный каталог раньше PATH. Результат `which` в старом тесте проверялся, но не использовался при запуске.

**Что это объясняет:** старый тест в текущей среде выбирал Microsoft launcher, а не найденный Git Bash; это конкретный воспроизведённый механизм непреднамеренного входа в WSL, согласующийся с процессами C121. **Что не доказано:** точные argv/дистрибутив исторической C121, текущее и прежнее состояние default Ubuntu во время C120, полная причинность исторического 180-секундного timeout. Нельзя заключать, что все предыдущие проблемы были вызваны только этим дефектом.

Мы раньше ошибочно считали результат `which` достаточным описанием исполняемого файла. Из-за этого диагностика ушла в общий контроль WSL вместо проверки bare-name lookup. Теперь дальнейший поиск timeout не должен автоматически зависеть от создания нового универсального watchdog.

## 4. Полный pytest: отдельная незакрытая проблема

В пределах ТЗ выполнен **ровно один** новый полный Windows запуск, с подробным выводом и внешним лимитом 180 s. Он снова не завершился: **180.157 s, timeout**, принудительный returncode 15. Ниже результат не выдаётся за pass.

Новый запуск собрал 938 тестов (12 добавлены к историческим 926), плюс 1 collection skip. В момент прерывания лог показывал ~48%, текущий nodeid:

`tests/unit/test_phase3_compare_v1_v2.py::test_retro_compare_complete_and_historical_v1`

Следовательно этот запуск исчерпал общий бюджет **раньше файлов bash**, а не завис на исправленном вызове. По одному последнему nodeid нельзя утверждать deadlock в этом тесте.

Две различающие адресные проверки после остановки:

1. Текущий nodeid отдельно: **1 passed, 5.35 s**, внешний wall 5.922 s.
2. Две существующие проверки CLI отклонения невалидных конфигов, без новой научной интеграции: **2 passed, 14.18 s**; call durations 6.89 s (`rotating_frame`) и 7.10 s (`wrong_output_origin`). Они не используют bash/WSL. В полном логе наблюдались многочисленные последовательные CLI subprocess.

Это подтверждает заметную накопленную стоимость, независимую от исправленного bash. **Не установлены** полное распределение времени по фазам, точное место внутренних задержек CLI, отсутствие зависимости от порядка и холодного кеша, необходимый полный бюджет. Нет основания просто повышать timeout или экстраполировать весь набор по двум тестам. Старые C120/C121 не переписываются.

При прерывании завершены только собственные наблюдавшиеся Windows PID с проверкой времени создания. По повторной проверке таких живых процессов не осталось. Наблюдённый пик RSS ~529 MB; память не была причиной остановки. В этом полном запуске наблюдались Python/git, не WSL, но polling не даёт универсальной гарантии обнаружения всех кратких процессов. Системные или чужие задачи не завершались. После явной Linux-регрессии отдельный `wsl --list --verbose` показал все четыре дистрибутива Stopped; мы не посылали им shutdown/terminate.

## 5. Бюджет, происхождение и следующий шаг

Новые Windows subprocess под ограниченной обёрткой суммарно **223.688 s**; отдельный Linux-профиль снаружи **7.875 s**. Контролируемый процессный lookup не возобновлял процессы. Для ранее выполненных частей T072 в обёртке зарезервировано **180 s** (консервативный резерв, не измерение прошлых запусков); резерв + текущие измерения <600 s. Небольшие операции трекера/метаданных отделены от тестовых длительностей. Новых больших наборов данных не создавалось.

Доказательства: `results/evidence/W2_T072_resolution_20261101T183920Z/`, включая input SHA, diff, suspended lookup, реестр попыток/потомков, stdout/stderr, полную незавершённую регрессию, отдельный последний nodeid, CLI durations, Windows/WSL адресные тесты и manifest.

**Следующий шаг T072:** измерить durations по setup/call/teardown и запуску CLI в ограниченных поднаборах; отделить ожидание процессов/импорты/I/O от стоимости собственно тестов. Изменения production CLI/научной логики не разрешены текущим ТЗ. Второй полный запуск не делать без новой обоснованной оценки и бюджета. Общая регрессия остаётся inconclusive, но проблема выбора неправильного bash исправлена и проверена.
