# W2-T072: контроль собственного Windows→WSL launcher

Дата 01.11.2026 UTC. Owner `pi-c120-launcher-20261101T183114Z`. Evidence ID `W2-T072-launcher-20261101T183114Z`; научного запуска нет.

## Что выполнено

Windows Python запустил **конкретную собственную** команду списком аргументов, без shell: `C:\Windows\System32\wsl.exe -d Ubuntu-24.04 --exec /usr/bin/python3 .../W2_T072_linux_owned_20261101T183114Z.py`. Windows launcher сохранил полный фактический argv, PID, cwd, SHA Linux-скрипта, returncode, wall и receipt в `results/evidence/W2_T072_launcher_20261101T183114Z/launcher.json`.

В Linux receipt `WSL_DISTRO_NAME=Ubuntu-24.04`, boot ID, PID/starttime/session/PGID своих supervisor, child/grandchild и отдельного sentinel. Supervisor создал child в отдельной группе, затем тот создал grandchild. Через 0.6 s supervisor перед SIGTERM проверил starttime и PGID лидера, а также наличие токена попытки в `/proc/<pid>/cmdline`. Получено: SIGTERM returncode −15, обе тестовые задачи не активны при проверке, собственный отдельный sentinel оставался активен до штатной уборки. Windows launcher завершился с returncode 0 за **6.297 s**; Linux-скрипт вернул 0 после собственного `finally` и ожидания sentinel.

Обе синтетические задачи ограничены собственным сном 4 s, включая случай внезапной смерти supervisor. Windows launcher ограничен 20 s и при таймауте завершает только собственный Windows `wsl.exe`, не останавливает дистрибутив. Реальный таймаут в этой проверке не произошёл. stdout/stderr сохранены отдельно; Ruff и LSP двух скриптов прошли.

После проверки `wsl --list --verbose`: **Ubuntu-24.04 Running**, Ubuntu (по умолчанию), kali-linux и docker-desktop Stopped. Намеренный локальный launcher мог запустить Ubuntu-24.04; дистрибутив не останавливался, поскольку может использоваться другими задачами пользователя. Активность дистрибутива не доказывает наличие оставшихся рабочих процессов проверки. Идентифицированные child/grandchild в момент проверки supervisor не были активны; независимо все процессы дистрибутива не перечислялись.

## Что не установлено

- Контролируется **только явно запущенный собственный launcher**. Старый pytest или Git bash не направляются через него; кто вызвал исторический `wsl.exe` и с какими аргументами остаётся неизвестным.
- Чтение `WSL_DISTRO_NAME` и явно переданный `-d` подтверждают этот собственный запуск, не историческую конфигурацию.
- Проверка токена относится к лидеру группы; процессы, отделившиеся через `setsid`, и произвольные потомки не охвачены. Нет независимого watchdog, теста SIGKILL supervisor, полного процесса атрибуции/cleanup при потере Windows launcher или нагрузки PID reuse. Состояние zombie не является активной задачей, но запись `/proc` может сохраняться.
- Успех проверки ограниченного synthetic сценария **не разрешает повтор исходного pytest** по T072; нельзя утверждать, что весь его WSL-маршрут перехвачен. Нет изменений F3–F5, научного кода, runner или завершённых runs. Целевая физика/научный допуск не проверялись.

## Дальнейший шаг

Нужен отдельный способ наблюдения **фактического** Windows процесса pytest/bash и безопасного управления возможными Linux-потомками, не сводимый к ручному запуску этого launcher. Пока механизм не доказан, C120 inconclusive; при невозможности обеспечить изоляцию оформить ограничение или согласовать другой подход, не выключая чужие WSL.
