## F1 — неизвестный вывод не равен пустому

`evaluate` принимает как известные только потоки точного типа `bytes` или `str`, возвращаемые штатным `subprocess.run` с захватом.

| Переданные значения | Результат |
|---|---|
| Оба потока явно пустые `b''` / `''` | Можно сохранить **синтетический** исход, только если прочие проверки также прошли |
| Хотя бы один `None` или неподдерживаемый тип | `admissible=False`, `outcome=unresolved`, причина `output_capture_unknown` |
| Известный непустой поток | `unclassified_output`, `unresolved` |
| Один поток неизвестен, другой известен и непуст | Обе причины сохраняются |

Неподдерживаемые ложные значения `False`, `0`, `[]`, `{}`, `bytearray()` и `memoryview(b'')` не приравниваются к пустому захваченному выводу. Непустой вывод не очищается и не классифицируется по тексту; белого списка нет.

Процессная регрессия запускает настоящий синтетический worker в режиме `stderr` с `os.write(2, ...)`, направляя stderr в отдельный файл, stdout в DEVNULL. `CompletedProcess.stdout/stderr` оба `None`, код выхода 0; содержимое файла подтверждает фактический вывод. V2 возвращает unresolved. Контроль с явно переданными прочитанными байтами stderr также блокируется, уже как `unclassified_output`.

**Граница:** `b''` — утверждение вызывающего кода о полученных данных, не доказательство полноты capture. Доказательство coverage, дочерние процессы, C-side без вывода, external kill и честность вызывающего кода здесь не реализованы.

## F2 — один снимок checkpoint

`verify_checkpoint` теперь:

1. Один раз вызывает `path.read_bytes()`.
2. Сверяет SHA-256 этих байтов с переданным закреплённым SHA.
3. Передаёт **те же байты** в `parse_json(raw)`, не открывая путь повторно.
4. Проверяет прежнюю структуру checkpoint и новый идентификатор схемы.

`parse_json` явно декодирует UTF-8, отклоняет duplicate keys (в том числе вложенные), NaN/Infinity, некорректный UTF-8, оборванный JSON и лишний второй документ. Строгий JSON-разбор не означает полную проверку семантики событий: это оставшаяся F4. `read_json` также использует этот разбор; JSONL журнала в данном шаге не ужесточался.

Детерминированный fault injection заменяет файл сразу после первого чтения:

- warning → чистый checkpoint: возвращается именно закреплённый warning-снимок;
- чистый → warning: возвращается именно закреплённый чистый снимок;
- комбинация закреплённого warning checkpoint с чистыми journal/receipt и чистой заменой файла **не принимается** в `evaluate`;
- resume из закреплённого partial warning checkpoint наследует warning, даже если путь уже содержит чистую замену;
- неверный SHA отвергается **до** JSON-разбора;
- checkpoint v1 и несовпадающий contract отвергаются.

Это проверка связи «SHA ↔ разобранный документ» при контролируемой подмене, **не настоящий состязательный многопроцессный тест**. Не обещается, что путь останется неизменным после чтения/возврата. Защита от произвольной подмены внешнего SHA/receipt, job/attempt binding и crash-consistency не добавлены.
